## Common working method

These rules come from the shared working-method repository and apply to every project that consumes it. Whatever a rule needs to know about *this* project — its forge repository, base and release branches, sprint tracking, documentation exception, public/private guard, CI workflow — is declared in the project's `workflow.config` (format: `.working-method/procedures/workflow-config.md`), never assumed.

1. **Code review by another LLM is mandatory before any merge.** The reviewer comes from a different vendor than the author (code written by Claude → reviewed by the model of `review.reviewer-for-claude` through the `agy` CLI in `--mode plan` without `--dangerously-skip-permissions`, so every shell command is refused to it (with that flag, a plain `grep` read a `.env`); plan mode is still not read-only (it has created files in its review copy), so only the isolated copy protects the repository; code written by Gemini → reviewed by the model of `review.reviewer-for-gemini`). The review runs in a **temporary export of the reviewed commit outside the repository** (`git archive`, with no `.git`, whose `gitdir` line would give the reviewer the repository's path), so the external reviewer can never read an ignored file such as `.env`, nor any path of `review.private-paths`; the project's public/private guard (`guard.command`), when it has one, runs on the reviewed scope first, and every file the reviewer adds, changes or deletes in the copy is reported. The report is a Gitea PR comment whose first line is `llm-review sha=<SHA> base=<base> model=<model> verdict=<pass|block>`; it is never committed. Reviews run through `.working-method/review/llm-review.sh`, in two stages: every story starts with a spec review (`--story <n.m>`: adversarial, structure and prose lenses on the story text), and every PR gets a code review (`<PR number>`: edge-case-hunter and verification-gap lenses plus the project layer, `review.project-layer`). In both, the reviewer applies the review method the project layer names; the author never reviews in its place. When the project tracks its sprint (`sprint.convention`), each story has a story file, `<sprint.stories-dir>/<story-key>.md`, whose `Status:` line matches the sprint status file and whose "Revue de spec" and "Revue du code" sections record every finding with its decision; deferred findings go to `deferred-work.md`.
2. **Documentation exception.** A PR whose every file matches `review.exempt-paths` needs green CI only, or the bootstrap substitute while CI does not exist (`ci.bootstrap`). The exception never covers any other file. `none` means no exception at all.
3. **Merge gates.** Nothing is merged without a review report on the head SHA with a non-blocking verdict, the public/private guard passing when the project has one, green CI once CI exists, and a consistent sprint status (statuses only in v1) when the project tracks one. A gate the project disables in `workflow.config` is shown as `inactif`: it does not block, and it never passes for green. `.working-method/gates/verify-and-merge-pr.sh` refuses any PR to the release branch (`forge.release-branch`): publication has its own path, written by the project. Who may run `--merge` is the project's rule, written in its own `AGENTS.md`. **Sprint status lives in the story's own PR:** the story's line in the sprint status file and the `Status:` line of its story file move to `in-progress` in the branch's first commit, to `review` in a commit made before the LLM review, and to `done` in a commit made after a passing review, just before merge. The review gate therefore accepts a report on the parent of the head SHA when the head commit is that single status commit: it changes only the sprint status file (the story's line from `review` to `done`, `last_updated`, and the epic's line when the story closes its epic) and the story file's `Status:` line (from `review` to `done`), and otherwise only adds lines to the story file and to `deferred-work.md` (review reports, the author's decision on each finding, deferred findings), checked line by line. Any other change after the review requires a new review.
4. **Secrets.** Every token, credential or secret the project needs (Gitea API token, anything else) is defined in the project's environment file (`forge.env-file`, usually `.env` at the repository root), which is never committed: it is gitignored, and rejected by the project's guard when it has one. A `.env.example` lists the variable names without values. Scripts load the file without printing any value; agents never print or copy a secret value into files, commits or conversation output. The `GITEA_*` API variables stay on the dev machine only, because Gitea rejects secret names starting with `GITEA_`, and CI jobs use their built-in token instead.
5. **A guard gets a test that fails without it.** It was never enough to demand this of a control: in the source project, five *guards* inside scripts, over three epics, guarded nothing — a `|| true` that swallowed grep's errors, an empty-list guard that never fired, a `\$request[^_]` rule that let `$request_uri` through, a repository check defeated by a symlink, and an image selection defeated by a filename git quotes. All five read as plausible; none was found by review. **The test must exercise the input the guard is meant to refuse**, not only one it accepts, and it must be run once with the guard removed to see it fail (source project, epic 5 retrospective, 21/09/2026).
6. **A rule that describes a tool's behaviour is true only once verified.** An architecture decision of the source project said to look for the string `GPS` in an image's bytes — a photo carrying real coordinates contains no such string, they live in binary inside EXIF — and prescribed a generator's `crop` where it described `fill`. Both read perfectly and were false. Before writing a tool's behaviour into a decision, run it (epic 5 retrospective).
7. **A finding of a known error class is a sweep order, not a line to patch.** One story of the source project took six review rounds and five blocking verdicts, and every one was a variant of the same question — *what does this condition not see?* A `grep` whose exit code was read as "not found" was fixed on one line while its twin sat three lines below; a non-ASCII path hole closed in the guard by an earlier retrospective reopened untouched in a new script written seven days later. So: when a review names an error class, the fix **starts** by searching the whole change for other instances of that class, and a finding about a *trigger condition* is answered by re-enumerating everything that condition lets through — not by adding the one case cited (epic 7 retrospective, 22/09/2026).
8. **A lesson does not carry itself into the twin file.** The material half of rule 7, and the one that keeps winning. In the source project, one library held the single list of image extensions precisely because two copies once let a file slip past a control — its own header said so; its twin, written later for PDFs, had no list at all, and two file names ended up in four files under four spellings. Rule 5 asks a guard for a test, and a fixture must resemble the real output; neither asks what the *sibling* already learned. When a file is written "like" another, walk the older one guard by guard and say, for each, whether the new one needs it — intention is not symmetry. **And the walk is written down, or it does not happen.** Knowing this rule is not applying it: one story wrote *"a fix in one place does not carry itself"* into a test, and the next story wrote that test's twin without taking its guard. So a story that writes a file "like" an existing one names the elder in its story file and lists its guards, saying for each whether the younger needs it. Three lines is the whole cost (epic 9 retrospective, 24/09/2026).
9. **Every finding gets a written decision — including the ones you refuse.** A reviewer once asked a story to add a changelog entry that no rule of that project required — but the rule was **real**: it lived in the reviewing account's own global memories, where it described another project. **The external reviewer carries its user's global instructions into a repository's isolated review**, so a verdict can block on a contract the project never signed; that is refuted by naming where the rule lives and why it does not apply here. Checking `AGENTS.md`, `docs/` and the architecture is not enough to call a rule invented. A finding with no recorded decision is indistinguishable from a finding nobody read, and the next reviewer raises it again. So the story file records **every** finding with its disposition: retained, refuted on evidence (with the evidence), deferred to `deferred-work.md`, or invalid because the rule it invokes does not exist (with what was checked to establish that). Silence is not a decision, **and a `pass` verdict is not a triage**: a report is a list to exhaust, whatever its verdict. **A PR that has no story — a retrospective's actions, a procedure, tooling — records the same thing on the pull request itself**, in its body or, once it is open, in a comment, since that is the only place a reader of that change will look. `create-pull-request.sh` writes a body only at creation and never updates it, so decisions taken after the first review land in a comment (epic 9 retrospective, 24/09/2026).
10. **A story's noisy loop runs in a sub-agent; the cross-cutting judgement does not.** Build logs, hundreds of test cases, browser measurements and eight review rounds fill the orchestrating context with material that has no value beyond the story producing it — and that context ran out mid-session in the source project. So the implementation loop is delegated: the sub-agent writes the code and the tests, runs the suite and the controls, and iterates on the review's findings. What stays with the orchestrator is what a fresh agent cannot do, and what actually fails: the spec-review triage, the arbitrations put to the project owner, **the twin-file brief of rule 8 — named explicitly in the sub-agent's prompt, because it cannot derive which sibling to walk** — the verification of the sub-agent's report against the repository, and the merge.

    Two things this is *not*. It is **not** a remedy for forgotten rules: isolating a story makes files never opened more likely, not less, which is exactly why the brief is the orchestrator's job. And it does **not** extend a merge delegation the project owner gave to the agent whose own audit proves what a second opinion would repeat: the orchestrator re-runs the gates itself on work it did not write, and merges.

    A sub-agent's report is an unverified claim, never an established fact. Before it becomes a merge argument, reopen the file, the commit, the test output.

The shared dev skills (`llm-review`, `create-pull-request`, `verify-and-merge-pr`, `sprint-consistency`) follow the three-level pattern `<skill dir>/<name>/SKILL.md` → `.working-method/procedures/<name>.md` → the script in `.working-method/`. Each skill must be available whatever the agent harness: `.working-method/bin/install` links it into every folder of `agents.skill-dirs` (for instance `.claude/skills/`, `.agents/skills/`), as relative symlinks to the one copy in the shared repository, so nothing drifts; it never overwrites a project's own skill of the same name. A project's own skills follow the same pattern inside the project. Every script follows `.working-method/procedures/shell-scripts.md` (rules and known shell pitfalls); shared logic lives in the shared repository's `lib/`, and its `tests/run.sh` replays the offline tests, on the dev machine and in CI.
