# Procédure — Écrire et tester les scripts shell

Les scripts du dépôt commun (`lib/`, `gitea/`, `gates/`, `review/`, `checks/`, `bin/`, `ci/`) et ceux des projets qui le consomment suivent les mêmes règles, dans le shell que chacun a déclaré (§ *Shell*, ci-dessous). Cette procédure les rassemble, avec les pièges déjà rencontrés et les tests qui les rejouent (story 0.9 du projet source, constat P1 de la rétrospective de son epic 0).

## Règles

- En tête, pour tout script en bash (tout le dépôt commun) : `#!/usr/bin/env bash` et `set -euo pipefail`. Un script qui lit un jeton coupe la trace (`set +x`) avant de charger `gitea/gitea.sh` (`gitea-token.md`). **bash 4.3 au minimum** (`local -n`) : `bin/check-bash` le vérifie avant la première ligne de bash (`runner-bash.md`).
- Un script se lance depuis n'importe quel dossier du projet et se place à sa racine (`config_project_root` de `lib/config.sh` : le dépôt git du dossier courant, ou le projet qui contient le dépôt commun quand on est dans le sous-module) avant de lire les fichiers suivis.
- **Ce qui est propre à un projet se lit dans son `workflow.config`** (`config_load`, puis `config_get`), jamais en dur : un nom de dépôt, une branche, un chemin, une commande. Le fichier est validé en entier avant toute action, et un refus sort en `2` (`workflow-config.md`).
- Un message commence par le nom du script. Aucun message n'affiche une valeur de `.env`, l'adresse de la forge ou un contenu privé.
- Identifiants en anglais ; messages, commentaires et procédures en français.
- Aucun outil de plus sans décision : `bash`, `git`, `jq`, `curl` sur le poste, `grep` et outils de base. Le runner de la forge est un Alpine en mode hôte, avec les outils de BusyBox et sans `jq` (`runner-bash.md`) : la CI y télécharge `jq` et `shellcheck`, épinglés par version et SHA-256 (`ci/ensure-jq.sh`, `ci/ensure-shellcheck.sh`).
- La logique commune vit dans `lib/` : `shell.sh` (enveloppes des outils lancés en boucle), `config.sh` (lecture et validation de `workflow.config`, racine du projet), `dotenv.sh` (lecture d'un fichier d'environnement), `sprint.sh` (lecture du suivi de sprint, sans `jq`), `require-bash.sh` (prérequis bash, en POSIX sh) ; puis `gitea/gitea.sh` (environnement, API de la forge, fichier de motifs, base d'une PR) et `gates/merge-gates.sh` (décisions des verrous de fusion).
- **Une parade s'écrit une fois.** Dupliquer une garde correcte est un défaut au même titre que l'oublier : la même lecture du code de `grep` avait fini en quatre exemplaires, dont le dernier est né le jour où l'avant-dernier a été écrit pour cette raison exacte (rétrospective de l'epic 3 du projet source). Avant d'écrire une enveloppe, chercher si elle existe dans `lib/shell.sh`.
- **Trois codes de sortie** (`0` conforme, `1` écart constaté, `2` je n'ai pas pu vérifier), légendés en en-tête de chaque script, avec une alerte hors du terminal devant un `2` : § *Codes de sortie*, ci-dessous.
- Une fonction de bibliothèque ne compte pas sur `set -e` et vérifie chaque étape : appelée derrière `||`, elle n'en profiterait pas. Elle répond par son code de retour, comme une commande, et n'écrit rien sur la sortie standard en cas d'erreur.
- Ce qui appelle la forge reste dans le script ; ce qui décide lit des fichiers. Une lecture paginée reçoit le nom de la fonction qui écrit une page : le script lui fait appeler la forge, les tests lui font lire des fixtures. Aucune variable d'environnement ne remplace un appel à la forge.

## Codes de sortie : trois, et une alerte

La convention vaut pour tout script qui vérifie, décide ou agit, du dépôt commun comme des projets (décision du 18/09/2026, appliquée le 06/10/2026). Chaque script l'écrit dans son en-tête, avec la liste de ses cas `1` et de ses cas `2`.

| Code | Sens |
|---|---|
| `0` | **conforme** : j'ai vérifié, rien à signaler ; ou l'action est faite |
| `1` | **écart constaté** : j'ai vérifié, et voici ce qui ne va pas ; ou l'état constaté interdit l'action |
| `2` | **anomalie** : je n'ai **pas pu** vérifier — usage, outil absent, configuration refusée, forge ou git illisibles, réponse inattendue |

- **Deux codes ne suffisent pas.** Avec `0` et `1`, « je n'ai pas pu vérifier » doit se ranger dans l'un des deux : rangé en `0`, le contrôle se désarme ; rangé en `1`, il bloque sur une panne d'outil, et on finit par le contourner. La question à se poser pour chaque refus : *l'ai-je constaté, ou n'ai-je pas pu le constater ?*
- **Dans les scripts qui chargent `gitea/gitea.sh`**, `die` sort en `2` et `refuse` en `1`. Un refus qui protège à raison ce qu'on s'apprêtait à envoyer ou publier (un motif privé, un chemin privé, le garde-fou) est un écart constaté : `refuse`.
- **Un consommateur garde le pire code** : `2` l'emporte sur `1`, et tout autre code non nul (`127`, un signal) compte pour `2` (`ci/checks-job.sh`). Jamais `|| exit 1` derrière un contrôle qui peut rendre `2`.
- ⚠️ **GNU make rend `2` sur toute recette en échec**, quel que soit le code de la recette : à travers une cible `make`, `1` et `2` se confondent. Ce qui doit distinguer les deux appelle le script, jamais une cible ; une cible qui lance un contrôle relaie son `2` par un message lisible (« anomalie (code 2) ») avant d'échouer.
- **Devant un `2`, on bloque et on alerte**, les deux. Bloquer sans alerter donne un refus qu'on ne comprend pas ; alerter sans bloquer laisse passer ce qu'on voulait arrêter. L'alerte sort du terminal qui a lancé la commande (décision du 06/10/2026) :
  - **en CI**, l'étape est rouge et écrit sa ligne `::error::`, que la forge affiche sur le job ;
  - **pour un gate lancé sur le poste** (`gates/verify-and-merge-pr.sh`, `review/llm-review.sh`), un commentaire sur la PR, publié par `alert_pr` (`gitea/gitea.sh`) dès que la PR est lue : quiconque ouvre la PR le voit. Le chemin du dépôt et du dossier personnel y sont masqués ; un message qui contient un motif privé n'est pas publié ;
  - **si la forge est injoignable**, c'est le `2` lui-même, et le terminal reste le seul canal : le script le dit.
- ⛔ **La sortie de secours est humaine, explicite et tracée** : seul le responsable du projet décide de passer outre un `2`, par écrit sur la PR, sur le modèle de la règle de hotfix. Jamais un contournement dans un script : pas d'option `--force`, pas de `|| true` sur un contrôle, pas de `--no-verify`.

## Shell : bash ici, celui que le projet déclare chez lui

- **Le dépôt commun est en bash** (décision du 30/09/2026) : ses scripts, ses bibliothèques (`lib/`, `gitea/gitea.sh`, `gates/merge-gates.sh`) et son harnais de tests. Un script de projet qui charge une de ces bibliothèques est donc en bash.
- **Un projet garde ses propres scripts dans le shell qu'il a déclaré**, dans son `AGENTS.md` ou sa documentation des tests, avec le shell qui les exécute réellement (dash sur un poste Debian ou Ubuntu, le `sh` de BusyBox sur un runner Alpine). Un projet peut ainsi garder ses scripts en **POSIX sh** ; il n'a pas à les réécrire pour consommer ce dépôt. Sans déclaration, la règle est bash.
- **En POSIX sh, ce qui remplace `pipefail`** : dash ne l'a pas, et le code d'un pipeline y est celui de sa dernière commande. La règle est donc **jamais de pipe sur un chemin qui décide** : la sortie d'une commande dont le code compte est lue dans une variable ou un fichier, son code testé, puis seulement filtrée. En tête : `set -eu`, ou une vérification explicite de chaque étape, que le script dit.
- **En POSIX sh, aucune construction de bash** : `[[ ]]`, tableaux, `local -n`, `<<<`, `< <(…)`, `${VAR:0:N}`. `sh -n` ne suffit pas à le vérifier (voir le tableau : dash accepte la syntaxe de `${VAR:0:N}` et le refuse à l'exécution). Les tests du projet lancent ses scripts sous le shell qui les exécute.
- **Ses tests passent quand même par le harnais commun**, qui est en bash : un adaptateur au format `case_<nom>` lance chaque test du projet dans le shell du projet. Le harnais est en bash, les scripts éprouvés gardent le leur.
- **En bash aussi, la règle « jamais de pipe sur un chemin qui décide » reste.** `pipefail` ne la remplace pas : il fait remonter l'échec de chaque élément, y compris celui d'un `grep` tué par SIGPIPE derrière un `head` (voir le tableau), si bien qu'un pipeline correct peut arrêter une étape sans un message.
- Toutes les autres règles de cette procédure valent quel que soit le shell : racine du projet, `workflow.config`, messages, une parade écrite une fois, un test par garde, un test et une ligne par piège.

## Tests

```bash
tests/run.sh                          # tous les cas du dépôt commun, arrêt au premier échec
tests/run.sh tests/test-sprint.sh     # les cas d'un fichier
ci/checks-job.sh                      # ce que lance la CI : tests, secrets, noms de projets, shellcheck
```

Depuis un projet, `.working-method/tests/run.sh <fichiers>` lance les tests du projet avec le même harnais.

Code de sortie : `0` tous les cas réussis ; `1` un cas échoue (le script nomme le fichier, le cas et affiche sa sortie) ; `2` tests impossibles à lancer (outil absent, fichier de test illisible, `workflow.config` refusé).

- **Quand** : avant toute PR, sur le poste ; dans la CI du dépôt commun, par `ci/checks-job.sh`, que le poste lance de la même façon.
- **Conditions** : aucun réseau, ni fichier d'environnement ni chemin privé ; dépendances `bash`, `git`, `jq`, `grep` et outils de base. Chaque cas tourne dans son propre processus bash, pour que `set -e` y reste actif (`tests/test-run.sh` le prouve : un `false` au milieu d'un cas le fait échouer, et un cas ne voit rien de l'état laissé par le précédent). Trois gardes de `run.sh` vérifient le reste, chacune prouvée par ses cas dans `tests/test-run.sh` :
  - **aucun vrai `docker`, `curl`, `psql` ni `ssh`** : de faux binaires, en tête du `PATH` de chaque cas, notent leur appel dans un journal dont ils portent le chemin absolu, et le cas échoue en nommant l'outil, **même s'il a avalé l'échec** (`|| true`), relié le faux par un lien ou vidé son environnement en gardant son `PATH` (`env -i PATH="$PATH"`). Un cas qui a besoin de l'un d'eux place son propre faux devant. Pour un script testé qui « télécharge » un fichier local, `file_only_curl <dossier>` écrit un `curl` qui sert les URL `file://` par le vrai binaire et passe toute URL d'un autre schéma au faux du lanceur ; une adresse sans schéma est refusée par `curl` lui-même (`--proto =file`) : le script testé n'a jamais le réseau. Un autre outil se demande nommément par `real_command <outil>`, qui parcourt le `PATH` sans les dossiers de faux du lanceur. ⚠️ Un cas qui remplace son `PATH` par des dossiers sans ces faux sort de la garde pour ce qu'il lance ainsi : un outil de ces dossiers y est le vrai. C'est aussi le cas d'un `env -i` sans `PATH`, où s'applique le `PATH` par défaut du système. Tout outil qu'il relie dans un `PATH` d'essai doit donc venir de `real_command`, de `file_only_curl` ou d'un faux ;
  - **l'état git du dépôt** : `git status --porcelain` (fichiers non suivis compris), l'empreinte des diffs de l'arbre et de l'index, `HEAD`, les branches, les étiquettes et la remise (`stash`) sont relevés avant et après la suite ; tout écart la fait échouer et s'affiche. Un dépôt déjà modifié avant la suite n'est pas un échec : seul l'écart compte. Les branches distantes ne sont pas relevées : un `fetch` lancé à côté ne fait pas échouer la suite ;
  - **les sorties que le projet protège** (`tests.protected-outputs` ; dans le projet source, `public/` et `build/`), ignorées par git et donc invisibles de la garde précédente : `run.sh` relève leur état avant et après, et échoue sur tout écart.
- **Ajouter un cas** : une fonction `case_<nom>` dans un fichier `tests/test-*.sh`, qui charge `tests/lib.sh` et se termine par `run_case "$@"`. Outils : `run` (code dans `rc`, sortie dans `out`, erreur dans `err`), `assert_eq`, `assert_contains`, `new_repo` et `commit_all` pour un dépôt git de test, `write_workflow_config <dossier> [champ=valeur | -champ]…` pour un `workflow.config` complet, `$work` pour les fichiers temporaires, `$fixtures` pour les fixtures voisines du fichier de test, `$common` pour la racine du dépôt commun, `$root` pour celle du dépôt qui porte le fichier de test, `real_command <outil>` pour le vrai binaire d'un outil que le lanceur remplace par un faux, `file_only_curl <dossier>` pour un `curl` réduit aux URL `file://`.
- **Chercher dans un fichier** : `shell_grep_into <variable> <arguments de grep>`, l'enveloppe commune (`lib/shell.sh`). Elle distingue « rien trouvé » d'une erreur de lecture — deux cas que `grep` rend par 1 et par 2 ou plus —, et remplit une variable de l'appelant plutôt que d'écrire sur la sortie standard : appelée dans `$(…)`, une fonction ne peut pas arrêter le cas, son `exit` ne quittant que le sous-shell. **Elle rend toujours 0**, y compris sans correspondance : l'absence se lit dans la variable, vide. C'est ce qui permet de l'appeler nue sous `set -e` sans `|| true` — le `|| true` est précisément ce que ces enveloppes existent pour supprimer, puisqu'il avalerait aussi l'erreur de lecture. Qui a besoin de distinguer les deux appelle `shell_grep_status`, qui rend le code de `grep`.
- **Un cas sans objet ici** : `skip_case "<raison>"` (code 3), ou `skip_if_root "<ce qui est rendu illisible>"`. Le cas n'échoue pas et ne se tait pas : le résumé de `run.sh` compte les ignorés et donne leur raison. Un cas ne doit jamais rendre un verdict différent selon l'endroit où la suite tourne — s'il le fait, il s'ignore en le disant.
- **Chaque garde a un test qui échoue sans elle** : le cas exerce l'entrée que la garde doit refuser, et il a été lancé une fois la garde retirée, pour le voir échouer.
- **Tout nouveau piège** reçoit un cas de test et une ligne dans le tableau ci-dessous.

## shellcheck

`ci/checks-job.sh` lance, par `ci/run-shellcheck.sh`, shellcheck sur tous les scripts suivis (`*.sh`, `bin/check-bash`, `bin/install`, `bin/install.bash`), **à tous les niveaux** — erreurs, avertissements, informations et style —, avec le binaire de `ci/ensure-shellcheck.sh` : version **0.11.0**, empreinte SHA-256 vérifiée, téléchargé dans le dossier temporaire du job, rien d'installé sur le runner ; sur le poste, un shellcheck déjà présent n'est retenu que s'il est exactement de cette version (décision d'Arnaud du 04/10/2026).

- **Pourquoi tous les niveaux** : les règles « information » sont précisément celles des pièges de ce dépôt — `A && B || C` lu comme un si-alors-sinon, un `$?` qui ne dit pas ce qu'on croit, une fonction jamais appelée. Bloquer sur les seules erreurs aurait laissé passer, au premier lancement, quatre `A && B || C` et quatorze apostrophes typographiques dans des chaînes entre apostrophes.
- **Aucune exclusion globale.** `.shellcheckrc` ne règle que la lecture des fichiers chargés (`source-path=SCRIPTDIR`, `external-sources=true`). Une exclusion s'écrit sur la commande qu'elle concerne, **avec sa raison** : `# shellcheck disable=SC2016 # script passé à un autre shell : ses « $ » s'y développent, pas ici`. Un constat qui se corrige se corrige ; une exclusion ne vaut que là où le code fait exactement ce que la règle croit être une erreur.
- ⛔ **Une directive ne s'insère jamais dans une commande continuée par `\`** : le commentaire termine la ligne, et la suite de la commande devient une commande à part. shellcheck le signale (SC1126) ; un `sed` qui insère des directives à l'aveugle le provoquerait.
- ⛔ **Un commentaire qui commence par le mot « shellcheck » est lu comme une directive** : `# shellcheck sur tous les scripts…` est une erreur de syntaxe pour shellcheck (SC1073), qui cesse alors d'analyser le fichier. Commencer la phrase autrement.
- ⛔ **bash 4.3, pas plus** : `tests/test-ci-checks.sh` cherche dans les scripts suivis les constructions apparues après 4.3 (`mapfile -d`, `local -`, `${x@Q}`, `inherit_errexit`, `wait -p`, `EPOCHSECONDS`…). Ce que ce relevé ne voit pas, c'est un **tableau vide sous `set -u`** : bash 4.3 le tient pour non défini et arrête le script sur `"${t[@]}"`. Écrire `${t[@]+"${t[@]}"}` partout où le tableau peut être vide. Pour vérifier : `docker run --rm -v "$PWD:/repo" -w /repo bash:4.3 bash -c 'apk add -q git jq coreutils curl && git config --global --add safe.directory /repo && bash tests/run.sh'` (deux cas trouvés ainsi le 04/10/2026, dans `bin/install.bash` et `checks/run-checks.sh`).
- Une bibliothèque chargée par `.` déclare son shell en première ligne (`# shellcheck shell=bash`, ou `sh` pour `lib/require-bash.sh`).
- Une variable remplie par référence (`config_get`, `config_project_root`) est déclarée avant (`root=""`) ou figée après (`readonly`) : shellcheck ne voit pas l'affectation faite par `local -n`.

## Pièges connus

La colonne « Trouvé à » renvoie aux stories du projet dont l'outillage est extrait (« story 0.7 »), ou cite le projet où le piège est né sous la forme `<alias>#<clé>` (`secrets.md`, *Citer un projet*) : ce dépôt est public, il ne nomme pas ses consommateurs mais dit où retrouver le constat. La colonne « Test » nomme le cas qui rejoue le piège dans ce dépôt, « en partie » quand il n'en prouve qu'un côté, ou « aucun ici ». Un piège dont le défaut n'est pas encore corrigé chez un consommateur reçoit son test avec la story qui le corrige, et la ligne le dit. Un piège constaté mais **non reproduit** le dit dans sa ligne, avec ce qui a été essayé : il n'a pas de test tant qu'il ne l'est pas, puisqu'un test qu'on ne peut pas voir rouge ne prouve rien, et il ne passe pas pour un fait établi (règle 6 du bloc commun d'`AGENTS.md`). Les pièges propres à la pile d'un projet (son conteneur, son cadre applicatif) vont dans un tableau de même forme chez lui, qui renvoie à celui-ci.

## En cas d'échec d'un test

Le lanceur affiche le fichier, le cas et sa sortie. Corriger le script, ou le test s'il décrivait mal le comportement voulu, puis relancer `tests/run.sh` en entier avant de pousser.
